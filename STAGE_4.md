# Этап 4

Этап дал **наблюдаемость** (логи и метрики), **укладку нагрузки** на БД и внешние сервисы, **тестовую опору** под API и воркеры, **воспроизводимый сценарий нагрузки** на API и **автоматические ворота качества в CI**. Ниже — что именно появилось в продукте и инфраструктуре, без инструкций по запуску.

---

## Логирование

Во всех сервисных процессах бэкенда одна **общая дисциплина** логов: структурированные записи, понятная метка процесса (API, бот, consumer поведения, воркер и планировщик Celery), настраиваемый уровень и человекочитаемый или JSON-формат в зависимости от окружения.

**API** даёт **сквозную трассировку запроса**: идентификатор запроса возвращается клиенту и попадает в логи, по каждому обращению есть краткая сводка (метод, путь, статус, время). Отдельно фиксируются **неуспешная проверка секрета бота** (без утечки секрета) и **неожиданные сбои** с полным стеком для разбора инцидентов. Обычные ответы API с кодом ошибки (4xx и штатные 5xx из логики) идут своим путём; отдельного «журнала бизнес-событий» вроде «поставил лайк» на этом уровне нет — это слой доступа и надёжности, а не аналитика продукта.

**Бот**, consumer и **Celery** подключены к той же схеме; при прогоне тестов логи по умолчанию тише, чтобы не зашумлять вывод.

## Метрики

У API есть эндпоинт в формате **Prometheus**; его можно отключить конфигурацией.

По **HTTP** видно объём трафика, коды ответов, распределение задержек и параллелизм обработки — с разрезом по **стабильным именам маршрутов**, чтобы не размазывать показатели по уникальным URL. Дополнительно сняты **события и инфраструктура**: успехи и ошибки отправки сообщений в брокер, отказы входа бота по секрету, исходы сценариев **discovery**, попытки **обратного геокодинга** по провайдерам и **занятость пула соединений с PostgreSQL** — чтобы связывать поведение API с давлением на БД и внешние вызовы.

## Мониторинг в Docker

Рядом с основным стеком добавлен **наблюдаемый контур**: Prometheus собирает метрики **приложения**, **PostgreSQL**, **RabbitMQ** и **MinIO**; Grafana уже знает источник данных и содержит **проектный дашборд** по приложению и типовые обзорные по остальным компонентам. Основной compose-подъём **не обязан** тащить этот слой — он подключается отдельно, когда нужен полный стек наблюдения.

## Оптимизации и I/O

**Лента и карточки.** Кандидаты в discovery подбираются **одним ранжирующим запросом**; расстояние до кандидатов считается **без отдельного запроса на каждого**. Карточки для списков пользователей (в том числе входящие лайки) подгружаются **пачкой**; ссылки на фото в S3 при необходимости получают подпись **параллельно**. Контекст «кто смотрит ленту» поднимается **за один заход** к данным пользователя и его настройкам поиска.

**Рейтинг.** Фоновый пересчёт укладывается в **короткие транзакции** вокруг реальной работы; массовый пересчёт не держит одну длинную блокировку на всю базу. Пересчёт одного пользователя **подтягивает нужные сущности и счётчики одним чтением** и записывает результат компактно.

**Соединения и внешние вызовы.** Настройки пула БД **одинаковы по смыслу** для API и воркеров. Геокодер к внешнему HTTP-сервису **переиспользует соединение**, а не открывает клиент на каждый вызов. Очередь предзагрузки в Redis при обновлении **обновляется одним пакетом команд**, а не десятком последовательных.

## Тесты и нагрузка

**Пирамида проверок.** Есть быстрые изолированные тесты, HTTP-тесты против реального приложения с подменой внешних зависимостей и слой с **настоящими Postgres и Redis** в контейнерах — последний автоматически отключается, если контейнерной среды нет, чтобы обычный прогон не ломался. Для сценариев регистрации и discovery есть **готовые построители данных** (в т.ч. «пользователь на шаге перед завершением регистрации»).

**Надёжность и качество.** Неверный или отсутствующий секрет бота к API даёт **401 без обращения к базе**. Набор тестов заточен так, чтобы **основной вес покрытия** приходился на API, данные и воркеры, а не на толстый слой Telegram-обработчиков.

**Нагрузка.** Есть **генерируемый сценарий JMeter**, который имитирует типичный путь бота: профиль, входящие лайки, следующая анкета, лайк или пропуск, с паузами «как человек» и допуском гонок при записи. Отчёт нагрузки различает **длину целого пользовательского сценария** (с паузами) и **время отдельных запросов** к API — чтобы не путать «медленный сценарий» с «медленным сервером».

## CI

На **каждый PR и push в основную ветку** в GitHub Actions автоматически прогоняется бэкенд-тестовый набор: **pytest с измерением покрытия** по коду API, общих библиотек и воркеров и **жёстким порогом не ниже 85%** — без выполнения этого условия пайплайн считается проваленным. В том же задании поднимается **RabbitMQ**, чтобы проверки, завязанные на брокер, не были «на честном слове».

Отдельным процессом на **main**, **релизных тегах** и по **ручному запуску** собираются и **публикуются контейнерные образы** API, бота и сервиса миграций в **GitHub Container Registry**: на основной ветке доступен тег «последний», на теги версий — образы для выпуска, плюс метки по коммиту, чтобы сопоставлять развёрнутый код с исходниками.
